# Living Phone Authenticity — next approved priority
November 25, 2026. Planning and authoring direction approved. Runtime integration follows Build 31 release stabilization. This spec is spoiler-free; private narrative documents own the actual chronology and causal explanations.

## Goal
A player should feel they are holding a real, actively used fictional phone, not a collection of clue screens. Creator's interpretation of the photos is that Nora appears to be using the phone normally. Preserve that subjective impression without confirming her current status, the origin of an event, or what is happening in the story. Do not rewrite canon to fit incidental generated imagery. Ordinary activity is meaningful as characterization even when not evidence.

## Prioritized execution checklist
- [ ] Audit each existing app for shallow content, generic responses, dead controls, missing chronology, implausible notifications, repeated records, cross-app contradictions and state leakage. Use neutral fixtures and report only technical findings.
- [ ] Build shared local fictional timeline/event catalog and stable record IDs. Distinguish recorded time, delivered time, displayed time, provenance, read state, authored claim vs verified evidence, gated content, historical activity vs newly delivered events. Use private authoring fixtures, deterministic clock/offset and save-compatible migrations. Never generate unapproved live activity as factual canon.
- [ ] Messages/Phone/Contacts: distinct voices, ordinary banter and personal/work conversations, multi-turn context, misunderstandings, follow-ups, incomplete messages, read/typing where appropriate, believable delays and silence, call history/voicemail and meaningful nonresponse; no universal response or repeated generic script. Clarify player's role/permissions; do not silently impersonate Nora. No real-world communication.
- [ ] Mail, Notes, Files, Calendar, Browser, Clock and other built-in apps: coherent ordinary records, mundane drafts, work and personal details, reminders, completed tasks, searches/bookmarks/history, attachments and source links. Match the same fictional events across relevant apps without exposing protected metadata. Not everything needs to cross-link or be a clue.
- [ ] Afterframe, Connective, CommonGround: deepen existing functional feeds, distinct communities, profiles and ongoing ordinary activity; private DMs and locked profiles only where authored/gated. Motionwell and Dayblink: bounded functional offline slices per approved media spec; approved icons but no empty shell or fake playback. No extra redundant social apps.
- [ ] Shared persistent notification center and delivery scheduler: per-app alerts, banners, lock-screen privacy, read/dismiss/history, badges, actual route, sound/haptics, sensible quiet periods and late-night rhythm. No flood, no replay on reopen/restore, no stale notifications on checkpoints, no random scares on mundane events. Foreground/background behavior and deterministic replay tested; never require real-world waiting for progression.
- [ ] Photos and private memories: curate approved non-explicit assets, consistent face/accessories/locations, meaningful but mostly ordinary imagery. Record actual authored metadata rather than guessed dates; no incidental generated artifacts promoted into clues. Respect protected albums and preview redaction.
- [ ] HavenWatch: implement local-only fixed-camera still archive (CAM01 front entrance, CAM02 living room, CAM03 balcony, CAM04 kitchen, CAM05 exterior doorbell). Use V2 paired reference artwork as provisional canonical candidates pending cross-room continuity QA; keep V1 alternate drafts separate. No actual camera, microphone, network, location or surveillance. Render camera names, timestamps, IR/grain, compression, connection indicators, accessible zoom, motion/event archive, fictional arm/disarm and notification history in-engine. No claim that stills are real live video. All events authored and gated; camera position never drifts accidentally. No sensitive/private surveillance imagery as voyeuristic reward.
- [ ] End-to-end authenticity review: typical ordinary use sessions and cross-app state transitions, different conversation intents and timing, app switches, lock/unlock, save/restore/force-close, accessibility, offline mode, notification tap routing, protected previews and clue reachability. Ensure no accidental plot implication or answer leaked. No spoilers in creator QA.
