# LAST SEEN — OS-first roadmap (2026-11-24)
**Current governing development direction. Supersedes story-first sequencing in older documents.** Preserve existing source, scripts, character portraits, save data and branch history. Do not rewrite or expand the horror narrative until the fictional phone is accepted by the owner on physical hardware. Existing stories are legacy development fixtures, not the mandated final plot.

## Product pillars
- The fictional smartphone is the game world, not a menu surrounding a chat game. A player should be able to explore a normal, coherent phone before anything frightening happens.
- Original fictional handset/OS branding and visual language; modern familiar gestures, not a pixel-for-pixel Apple or SIMULACRA clone. The OS name, owner identity, visual concepts and final story require owner approval. SIMULACRA is a reference for immersion only (https://apps.apple.com/us/app/simulacra/id1252035454).
- Free complete game, no ads, paywalls, required accounts, paid runtime AI/API, or network dependence. All media and narrative run locally. Native SwiftUI/iOS 16+, portrait, preserve application identity and existing install/save compatibility.
- All world contacts, network, media, calls and settings are fictional/in-app; no real contacts, camera roll, messages, location, calls, network settings or system impersonation. Microphone and speech recognition remain disabled unless a future optional feature genuinely requires them. Actual local notifications opt-in and clearly branded LAST SEEN; fictional calls in-app only. Provide an accessible way to leave the simulation, content warning and intensity controls.


## Approved opening direction — new phone, wrong backup (2026-11-24)
The player believes they have purchased a new fictional smartphone. First launch begins with an original device setup assistant: welcome, fictional device preferences, wallpaper, and transfer/restore. A simulated cloud service restores a bundled snapshot incorrectly associated with the player's fictional device. The initial restore looks ordinary, with progress, categories and app preparation; the player is not explicitly told whose data it is. The first home screen is the restored phone, not a case menu. Everyday browsing reveals that the contacts, photos, notes, appointments, messages and eventually videos belong to an unfamiliar woman. Owner name, identity, reason for the mismatch, final script and ending remain open. Build onboarding mechanics and neutral fixture first, not the horror reveal. No actual Apple/iCloud branding, login, credentials, phone number, cloud access, network or real user data. Allow a locally stored fictional device nickname; never require the player's real name. Restore animation is entirely fictional and local. Persist completion, resume interrupted restore idempotently, provide reduced-motion/skip-animation accessibility and preserve existing lab and story data. Non-destructive setup replay from Settings does not delete saves. A small provisional female-owner snapshot now exists for OS testing; expand it after the phone shell is stable.

## Approved direction — fictional desktop recovery and physical connection prologue
Before the in-world welcome screen, after a clearly branded out-of-fiction consent review, the player receives a phone brought to them for servicing. Present a compact original Windows-inspired computer desktop and fictional jailbreak utility. Use authentic non-operational jailbreak vocabulary (diagnostics, recovery mode, bootstrap, userspace, package manager, respring, icon cache, verbose boot) and original names/logos; do not ship real exploits, commands, USB access, copied tools or actual system changes. Community projects such as checkra1n, Dopamine, unc0ver, Sileo and Filza are cultural inspiration only. Final tool branding pending approval.
- Physical immersion: ask the player to connect their iPhone to power using its ordinary charging cable. Use public UIKit UIDevice battery monitoring and batteryStateDidChangeNotification during the connection stage only. Treat .charging or .full as externally powered; .unplugged as disconnected; .unknown as unavailable. This is a power-state proxy, not proof of USB data connection, cable type, computer identity, or real jailbreak. Wireless charging may also satisfy it. Never inspect or transfer actual USB data or require a computer, jailbreak, permission prompt or private API.
- If already powered on entry, recognize it immediately; otherwise wait for a real power-state transition, with simulated connection sound/haptic (respect preferences), device card and diagnostic progress. Always offer accessible Continue without cable (simulated connection), including unknown state, simulator and no charger. Do not require unplug/replug, and do not block completion.
- Optional unplug during fictional install: pause the animation with a recoverable reconnect/continue-simulated prompt; never fake real hardware damage, erase data or perform a real reboot. Persist progress, restore monitoring settings on exit, support reduced motion and skip. Use deterministic fictional records and no actual personal device identifiers.
- Flow: device connection -> diagnostics -> install fictional custom environment/bootstrap -> optional short animated reboot -> existing welcome/personalization -> mistaken local backup restore -> ordinary phone exploration -> discover previous owner's fictional passcode -> in-game appearance enrollment and optional real biometric convenience. Keep prologue short, initially mundane, with no mandatory horror or final clue narrative before OS approval.
- Later: original offline package manager, bundled free themes/tweaks, fictional logs, filesystem browser, optional return to desktop for archived backup puzzles. All simulated, local and free.
- QA: unplugged/plugged/full/wireless/already connected/unknown; fallback; interrupted animation/relaunch; no repeated onboarding; preserve earlier saves and consent. Hardware test on iPhone 16e; verify real status bar remains visible, no real USB operations or jailbreak dependency. Initial source implementation in Build 13; CI and physical QA pending.

## Approved security progression — discover owner passcode, then enroll appearance in-game
Supersedes the unrestricted biometric unlock direction for the final game. Build 12 remains a technical prototype for testing native authentication; do not cancel its active CI. Next security feature pass:
- Initial permissions review may offer optional system biometric authorization for later use, but never grants fictional owner privileges. Restore opens ordinary public apps and content; protected settings, private albums, locked notes and selected documents remain gated. The player must have sufficient accessible clues before any gate; avoid circular dependencies or mandatory biometrics.
- Discover the previous owner's fictional six-digit passcode through coherent cross-app clues. No real device passcode requests, no real accounts, no attempts to modify iOS security settings. Use a dedicated in-game keypad with masked entry, delete, cancel, retry and recoverable attempt cooldown; never permanently lock out or destroy progress. Final passcode and clues require narrative approval; use a neutral fixture for Phone Lab.
- Correct fictional passcode authorizes the in-game Security settings. Player can choose Add appearance (fictional animation, then genuine iOS LocalAuthentication of the already enrolled real device owner on explicit consent). No actual biometric enrollment API, facial scans, images or templates collected, no camera requirement. System authentication success enables the in-game biometric convenience flag only after correct passcode. Cancel/failure/unavailable/denial leaves fictional passcode fallback fully playable. Never conflate system biometric success with story authorization.
- Model separate persisted states: owner passcode discovered/verified, fictional enrollment enabled, and per-session protected access. Native authorization preferences alone cannot bypass the story gate; swipe, notification deep links, app switcher, replay, relaunch and direct navigation must enforce the same guard. Locking clears session access but preserves earned progression. Existing prototype saves migrate safely without silently granting fictional owner access.
- After fictional enrollment, authenticate on protected app entry or phone unlock, with the discovered fictional passcode always available. No authenticating against real face identity of Nora. No fake system permission prompt or real device credential entry. Add accessible in-game keypad, hints, reduced motion and explicit fallback.
- Test state transitions, wrong/right passcode, no premature biometric access, failed/cancelled auth, fallback, persistence/migration and all alternate entry paths. Physical Face ID QA on iPhone 16e. Implement security mechanics before writing final clue narrative.
